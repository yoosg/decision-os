Critical Adversarial · Gap-5
LLM Provider Interface 메서드 시그니처 미정의

AD-6는 "LLM Provider Interface로 공급자 추상화"를 선언하지만 인터페이스의 메서드명, 입력 파라미터, 반환 타입, 에러 계약을 전혀 명시하지 않습니다.

충돌 시나리오: 병원 영수증 팀이 generate(prompt: str) → str을 구현하고, 다음 Review 타입 팀이 complete(messages: list[dict]) → dict를 구현합니다. 두 코드 모두 AD-6를 준수하지만, Provider 교체 시 모든 ReviewContextBuilder가 깨집니다.

필요한 규칙: Provider Interface의 추상 메서드 시그니처(최소: 입력 타입, 반환 타입, 에러 클래스) 1개를 AD에 고정해야 합니다.

새 AD 추가 필요
Critical Adversarial · Gap-1
context_snapshot / result JSONB 봉투 스키마 미정의

AD-4는 공통 reviews 테이블의 두 JSONB 컬럼에 어떤 최상위 봉투 구조를 강제해야 하는지 명시하지 않습니다.

충돌 시나리오: 영수증 Review 빌더가 {"items": [...], "total": 0}를, 갱신 검토 빌더가 {"type": "renewal", "data": {...}}를 result에 저장합니다. 대시보드와 향후 Memory 추출기는 두 형식을 모두 파싱해야 하며, 공통 소비자가 존재하는 순간 깨집니다.

필요한 규칙: 최소 봉투 { "schema_version": int, "review_type": str, "payload": {...} }를 AD에 고정해야 합니다.

AD-4 규칙 강화 필요
Critical Adversarial · Gap-7
"AI가 생성한" 쓰기 경계 — 프론트엔드 직접 쓰기 허점

AD-3의 Prevents는 "Next.js의 직접 쓰기"를 막지만, Rule은 이를 "AI가 생성한 Review·Decision·Outcome 변경"으로 좁힙니다. 이 두 문장 사이에 허점이 생깁니다.

충돌 시나리오: 프론트엔드 개발자가 사용자가 시작하는 "Review 취소" 기능을 구현할 때, "이건 AI가 생성한 것이 아니라 사용자 액션"이라고 합리화하여 Supabase 클라이언트로 status를 직접 업데이트합니다. 이로 인해 아직 실행 중인 BackgroundTask와 경쟁 조건(race condition)이 발생합니다.

필요한 규칙: "모든 reviews·decisions·outcomes 테이블 쓰기는 사용자 주도이든 AI 주도이든 관계없이 FastAPI 경유"로 Prevents를 일관되게 확장해야 합니다.

AD-3 Rule 수정 필요
Critical Adversarial · Gap-4
RLS 구현 패턴 — 팀별 상이한 Join 방식

AD-3는 RLS 존재를 의무화하지만 어떻게 작성할지는 명시하지 않습니다.

충돌 시나리오: 보험 팀은 projects를 통한 서브쿼리 방식 EXISTS (SELECT 1 FROM projects WHERE id = project_id AND user_id = auth.uid())을 사용하고, 커리어 팀은 user_id를 테이블에 직접 비정규화하여 user_id = auth.uid()로 체크합니다. 레코드 재할당 시나리오에서 두 정책의 보안 의미가 달라집니다.

필요한 규칙: Playbook 테이블의 표준 RLS join 패턴(project_id → projects.user_id 방식) 1개를 고정해야 합니다.

새 AD 추가 필요
Critical Rubric Walker
보안 포지션 — 금융·의료 데이터 처리 AD 전무

병원 영수증(민감 의료 정보)과 보험 계약(금융 데이터)을 처리하는 시스템임에도 보안 관련 아키텍처 결정이 전혀 없습니다.

누락된 결정들: 파일 업로드 유효성 검사(파일 타입·크기 제한, 악성 콘텐츠 차단), LLM 프롬프트 인젝션 방어, API 인증 헤더 컨벤션, 시크릿 관리(Railway 환경변수 vs. 외부 vault), PIPA(개인정보 보호법) 준수 기준.

두 개발자가 파일 업로드 처리 방식을 각자 구현하면 보안 특성이 달라집니다.

High Tech Currency
OpenAI API 방식 — Chat Completions → Responses API 전환 권고

OpenAI는 2025년부터 모든 신규 프로젝트에 Responses API를 공식 권장하며, Assistants API는 2026년 중 종료(sunset) 예정입니다. 향후 신규 모델 기능(멀티모달, built-in 파일 검색 등)은 Responses API에 우선 탑재됩니다.

AD-6의 Provider Interface 추상화 덕분에 교체 비용은 낮으나, 처음부터 Responses API를 구현 대상으로 명시해야 Interface 시그니처가 올바르게 설계됩니다.

AD-6 또는 새 AD에 Responses API 명시
High Tech Currency
Railway — 2026년 프로덕션 안정성 이슈

Railway는 2026년 들어 복수의 장시간 다운타임, 스택된 배포, 무음 크론 실패, 엣지 라우팅 버그가 독립적으로 보고되었습니다. 파일 처리와 장시간 실행 작업(BackgroundTask)을 포함하는 앱에 특히 위험 요소로 지적됩니다.

권고: MVP/프로토타입은 Railway 유지, 다만 AD-2에 "Railway = MVP 전용, 프로덕션 스케일 시 Vercel(Next.js) + Render 또는 Fly.io(FastAPI)로 이전" 조건을 명시해야 합니다.

AD-2 Rule에 배포 이전 조건 추가
High Rubric Walker
테스트 전략 AD 부재

비동기 BackgroundTask + LLM 추상화 + 읽기/쓰기 분리 접근이 맞물린 구조는 여러 가지 테스트 방식이 가능합니다. 테스트 전략이 명시되지 않으면 두 개발자가 충돌하는 테스트 패턴을 도입합니다.

예: 한 명은 DB를 실제로 연결하는 통합 테스트를, 다른 한 명은 LLM을 모킹하는 단위 테스트를 기본으로 삼으면 CI 파이프라인 구성부터 충돌합니다.

테스트 전략 AD 추가
High Rubric Walker
관찰 가능성(Observability) / 로깅 AD 부재

pending → processing → completed | failed 상태 머신이 있는 비동기 시스템에서 "stuck in processing" 감지 방법이 없으면 운영 불능입니다. 구조화 로깅 형식, 에러 추적 툴, Review 실패 알림 경로 중 어느 것도 결정되어 있지 않습니다.

관찰 가능성 AD 추가

AD-4 Rule은 "새 Playbook = 새 테이블 세트 + project_id FK"만 요구합니다. 보험과 커리어 팀이 날짜 타입(timestamptz vs. date), 금액 타입(integer cents vs. numeric), 컬럼 명명 규칙을 각자 선택하면 크로스-Playbook 기능 작업 시 재협상이 필요합니다.

Medium Rubric Walker
보험증권 이미지 파싱 방식 — Deferred 분류 재검토 필요

Deferred 항목 "보험증권 이미지 파싱 방식 (OCR vs LLM)"은 실제로는 MVP 가정으로, PRD에서 FR-1.2로 포함됩니다. OCR-as-service vs. LLM 멀티모달 선택은 ReviewContextBuilder의 모듈 구조를 결정하므로 구현 시작 전에 결정이 필요합니다.

Deferred에서 MVP 착수 조건으로 이동
Medium Tech Currency
BackgroundTasks 스케일 업그레이드 경로 미명시 (ARQ)

Deferred에 "메시지 브로커 (Redis/Celery)"가 있으나 Celery는 2026년 기준 네이티브 async/await를 미지원입니다. FastAPI와 조합 시 표준 업그레이드 경로는 ARQ(async Redis Queue)입니다. 잘못된 업그레이드 경로를 Deferred에 기록해 두면 이후 혼란을 야기합니다.

Deferred의 "Redis/Celery" → "ARQ (async Redis Queue)"로 수정
Medium Tech Currency
pgvector 인덱스 타입 미명시 (IVFFlat → HNSW)

Supabase pgvector에서 현재 권장 인덱스는 HNSW입니다(IVFFlat는 레거시). 구현 시 잘못된 인덱스를 생성하면 이후 재인덱싱이 필요합니다. 간단한 구현 노트로 해소 가능합니다.

AD-2 또는 구현 가이드에 HNSW 명시
Medium Tech Currency
OpenAI 모델 티어 미명시

AD-2/AD-6에 "OpenAI (MVP)"만 명시되어 있고 어떤 모델 패밀리(GPT-4o, o-series 등)를 기본으로 하는지 결정되어 있지 않습니다. 모델 미지정 시 개발자마다 다른 모델을 사용하면 비용과 성능 특성이 달라집니다.

구현 착수 전 기본 모델 티어 결정
