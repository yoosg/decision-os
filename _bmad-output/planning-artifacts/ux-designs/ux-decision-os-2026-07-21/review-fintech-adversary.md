# Fintech/Insurance UX Adversarial Review — Decision OS
**Reviewer:** Fintech/Insurance UX Adversary
**Date:** 2026-07-21

## Overall verdict

Decision OS is thoughtfully designed for a calm, deliberate user who reads every word — but the real Korean insurance user is tired, confused, and wants the answer fast. The spec's "Conclusion first" voice principle actively undermines every safety mechanism designed to prevent impulsive decisions: the Review title ("보험금 청구 가능합니다") and the Context Sticky Bar recommendation text ("추천: 실손보험 청구 권장") are visible before the user reads a single line of evidence, which means the product leads with a conclusion it isn't yet legally or factually authorized to make. Regulatory language risk is the most acute unresolved issue; the spec contains no mandated legal disclaimer text, no definition of claim-recommendation scope, and no handling of the denied-claim scenario that will occur for a statistically meaningful fraction of early users.

---

## 1. AI Trust & Responsibility Framing — Critical

### Findings

- **Critical** The "Conclusion first" voice principle ("보험금 청구가 가능합니다" leads the screen — EXPERIENCE.md line 84) is directly in tension with the "Honest AI" principle. The Review title is the first thing a user reads. If the title asserts a positive claim outcome before the user has seen the Honest Box, then every subsequent disclaimer is fighting against an already-formed cognitive anchor. A user who reads the title, sees the sticky bar say "추천: 실손보험 청구 권장", and skips the body sections will have received what functionally feels like a guarantee — before any uncertainty framing. *Fix:* Titles should state possibility, not conclusion: "청구 가능성 검토 — 2건 해당 가능" rather than "보험금 청구 가능합니다". Apply this constraint as a hard rule for AI title generation.

- **Critical** The Context Sticky Bar displays the recommendation summary ("추천: 실손보험 청구 권장") in both the disabled and enabled states — EXPERIENCE.md line 117: "The bar always displays the current Review's primary recommendation as a summary label ... This text is present in both states." A user who opens the Review screen sees the recommendation before they have read one word of evidence or risk. The disabled CTA is the friction mechanism, but the recommendation is already served. This is the equivalent of a financial advisor announcing the recommended trade the moment a client walks in, then saying "but let me explain the risks first." *Fix:* In the disabled state, replace the recommendation text with a neutral label: "분석 내용을 먼저 읽어 주세요." Reveal the recommendation text only upon sticky bar activation.

- **Major** The Honest Box is positioned as "always the last section before the data reference timestamp" (EXPERIENCE.md line 218). Placing uncertainty last, after the Summary, Recommendation, and Evidence, means users who skimmed to the scroll-activation threshold (which only requires scrolling those sections into viewport, not reading them) may tap 채택 with no meaningful engagement with the Honest Box content. The section enters viewport during the scroll that activates the CTA, but there is no mechanism requiring the user to pause on it. *Fix:* Move the Honest Box to immediately after the Recommendation section, before Evidence. Uncertainty should qualify the recommendation, not trail it.

- **Major** The spec defines Honest Box tone as "direct, not apologetic" and explicitly states "It is not a warning and does not imply the Review is unreliable" (EXPERIENCE.md line 86). This framing, while well-intentioned for anxiety reduction, actively minimizes the epistemic weight of the uncertainty disclosure. If the AI could not verify the specific policy clause that governs the claim, that is a load-bearing gap — not a "feature." Soft-pedaling it as "direct" rather than "important" risks users treating it as boilerplate. *Fix:* Add a visual weight differentiator for high-consequence uncertainty (e.g., a policy-clause gap) versus low-consequence uncertainty (e.g., an unconfirmed hospital name). The spec currently treats all HonestBox entries as equally low-severity.

- **Minor** The "Short Review exception" (EXPERIENCE.md line 127: "If the Review content fits in a single viewport without scrolling, the bar is enabled from the moment the screen loads") creates a CTA path with zero forced engagement. The spec does not define what makes a Review eligible for the "short" classification, which means the AI backend controls this gate. If short Reviews are generated for any claim type — even consequential ones — the protection mechanism is bypassed entirely. *Fix:* Define explicit criteria for Short Review eligibility (e.g., claim amount below a threshold AND uncertainty is nil) and prohibit Short Review classification for any Review containing an HonestBox entry.

## 2. FSC Regulatory Language Risk — Critical

### Findings

- **Critical** The spec contains no mandated legal disclaimer text anywhere on the Review screen or the Decision 확인 screen. The microcopy table (EXPERIENCE.md line 100) includes "AI 분석 결과는 참고 정보입니다" as a "Do" example, but this appears only in a table of preferred phrasings — it is not specified as a persistent, mandatory UI element on any screen. Under 보험업법 Article 83, providing insurance solicitation without a license is a criminal offense; "청구 권장" language from an AI system that users act on could be interpreted as unlicensed solicitation. Without a mandated disclaimer that is anchored to every Review output, this is unmitigated legal exposure. *Fix:* Specify a mandatory, non-dismissable legal disclaimer line on the Review 상세 screen and the 서류 Checklist screen: "본 분석은 참고 정보이며, 보험사의 최종 심사 기준과 다를 수 있습니다. Decision OS는 보험 모집 또는 중개 행위를 하지 않습니다." This must be a design component, not optional copy.

- **Critical** The Decision option "채택 — 청구 진행" (EXPERIENCE.md line 256: "Proceeds to 서류 Checklist → 결과 대기") and the 서류 Checklist screen status banner "보험사 앱에서 청구 후, 결과를 입력해 주세요" (EXPERIENCE.md line 260) imply the app facilitates a claim without making it explicit enough that the claim act is entirely the user's own independent action through the insurer's channel. The word "청구 진행" in the CTA implies the app is an actor in the claim process. A regulator examining the product could interpret this as claim-assistance activity. *Fix:* Rename the Decision CTA from "채택" to "채택 — 청구 직접 진행" and add a single-sentence screen header on the Checklist: "다음 단계는 보험사 앱 또는 보험사 직접 창구에서 진행합니다. Decision OS는 청구 절차에 관여하지 않습니다."

- **Critical** The spec has no specified UX path for the denied-claim outcome in relation to the AI's prior recommendation. The Outcome input screen (EXPERIENCE.md line 425-430) records "거절" as a valid outcome, but there is no specified copy or design treatment that addresses the user's likely question: "AI가 가능하다고 했는데 왜 거절됐나요?" A user who followed the AI's "청구 가능합니다" conclusion and got a denial is now holding an experience of AI-caused financial disappointment with no explanation. In Korean fintech, this becomes a trust-destruction moment that spreads via app reviews and KakaoTalk. *Fix:* Specify a 거절 Outcome screen with contextual copy: "이번 청구가 거절됐습니다. AI 분석은 참고 정보이며, 보험사의 심사 기준에 따라 결과가 다를 수 있습니다. 거절 사유를 기록하면 다음 분석에 반영됩니다." Add a "거절 사유 입력" field as optional but prominent.

- **Major** The spec's microcopy prohibits "청구하지 않으면 손해입니다" (EXPERIENCE.md line 93) but does not address a subtler version: the Review title "보험금 청구 가능합니다" itself carries an implicit loss-aversion framing once the user understands that inaction means unclaimed money. The prohibition on urgency language is in the "Don't" column but the affirmative "가능합니다" framing in the "Do" column achieves the same behavioral effect — it primes the user to feel loss if they don't act. Under FSC guidance on fair treatment of financial consumers (금융소비자보호법 Article 19), the distinction between "informing of possibility" and "inducing to act" is a matter of context and prominence, not just word choice. *Fix:* All Review titles should be explicitly possibility-framed in spec constraints given to the AI generation system: require "가능성이 있습니다" or "해당될 수 있습니다" rather than declarative "가능합니다."

- **Minor** The 보험 건강도 점수 (Health Score Card) generates a 0–100 "AI-generated integer" (EXPERIENCE.md line 191) with a disclaimer that it "is AI-generated and is a reference indicator." This score, if users share it (e.g., "내 보험 점수 82점"), could create consumer expectations around a standardized metric that does not exist. Under 금융소비자보호법, making comparative financial assessments that imply a regulatory or industry standard baseline when none exists can be characterized as misleading representation. *Fix:* The Health Score disclaimer must include "보험업법상 인가된 평가 지표가 아닙니다" and the score methodology must be disclosed on demand (accessible from the Health Score Card via an info icon).

## 3. Anxiety Management — Major

### Findings

- **Major** The spec contains no treatment of the most common Korean insurance psychology concern: "청구하면 다음 갱신 때 보험료가 오르나요?" (Will claiming affect my future premium?). The "Minimize anxiety" principle is stated (EXPERIENCE.md line 34) and urgency language is prohibited, but the primary source of anxiety for Korean real-money insurance decisions — fear of premium retaliation — is completely unaddressed. A user reading a "청구 권장" Review who worries about this will either not act (false negative) or act in confusion. *Fix:* The Review 상세 spec must include a mandatory field for the AI to address premium impact: either a factual statement ("이 보험 상품의 청구 이력은 갱신 보험료에 영향을 주지 않습니다" or "영향을 줄 수 있습니다") or an HonestBox entry acknowledging the AI cannot determine this. Silence on this question is an anxiety amplifier.

- **Major** The document checklist on the Decision 확인 screen (EXPERIENCE.md line 476: "진단서 미체크, 진료비 영수증 체크됨, 개인정보 활용동의서 미체크") has no specified UX for missing documents. If a user realizes on the checklist screen that they cannot get a required document (e.g., the hospital is closed, the diagnostic certificate costs extra money, the treatment was months ago and records may not be available), there is no guidance path. The checklist sits in a "결과 대기" state with no escape route and no instructions. *Fix:* Each checklist item must have an expandable "이 서류를 구하기 어렵다면" help row specifying alternatives or the consequence of omission. The checklist screen needs a secondary CTA: "서류 준비가 어려워요" that routes to contextual Chat on this specific screen.

- **Major** The analysis loading state says "분析 중입니다. 앱을 닫아도 됩니다." (EXPERIENCE.md line 244) — well-designed. But the spec defines no timeout, no failure state, and no user notification for the case where the AI analysis never completes or completes with an error after the user has closed the app. The Flow 1 narrative assumes seamless delivery. In a production system, background job failures are not rare. A user who confirmed an event, closed the app, and returns an hour later to find no Review card and no error has no mental model for what happened. *Fix:* Define a maximum analysis window (e.g., 5 minutes). If exceeded: push notification "분析을 완료하지 못했습니다. 앱에서 확인해 주세요" + Inbox error card with "다시 분析하기" CTA. Specify the error screen in the State Patterns table.

- **Minor** The onboarding trust signals screen (EXPERIENCE.md line 501: "비밀번호는 저장하지 않습니다." / "언제든지 연동을 해제할 수 있습니다.") addresses credential storage and data portability but says nothing about where the health + financial data is stored, who can access it, or how it is encrypted. Korean users who have experienced financial data breaches (e.g., the 2014 카드사 개인정보 유출 incident still affects user psychology) will have implicit questions the two trust signal sentences do not answer. *Fix:* Add a third trust signal: "회원님의 데이터는 국내 서버에 암호화 보관됩니다." and add a tappable "개인정보 처리방침" link in small text below the trust signals (not a full modal — just a link).

- **Minor** The "무시" decision has no confirmation dialog and no consequence shown (EXPERIENCE.md line 258: "Review archived. Removed from Inbox. No confirmation dialog."). The rationale given is that the action is "reversible via Memory." However, the user likely does not know it is reversible, and for a claim Review — where ignoring a valid claim means leaving money uncollected — the absence of any friction or information is a poor outcome. "무시" on a financial action feels permanent to most users. *Fix:* After the "무시" tap, show a single-line toast (non-blocking, 3 seconds): "이 Review는 메모리에서 다시 볼 수 있습니다." This is the minimum viable signal that the action is not destructive.

## 4. CODEF API Failure UX — Major

### Findings

- **Major** The spec defines only one CODEF failure path: timeout/error → "자동 연동에 실패했습니다" screen with "직접 입력할게요" CTA (EXPERIENCE.md line 267). It does not address partial success: CODEF returns data for 3 of a user's 5 policies. The AI then generates a Health Score and initial Review based on incomplete insurance coverage data, with no indication to the user that the assessment is incomplete. A user with an uncaptured critical illness rider will receive a Review that does not reference that coverage — and may make a real financial decision (decide not to claim because the AI said no coverage exists for this event) based on the gap. *Fix:* The CODEF integration result screen must display the count of policies successfully retrieved versus expected, and the HonestBox in the initial Review must contain a mandatory entry: "연동된 보험 정보에 기반한 분析입니다. 미연동 보험이 있는 경우 해당 보장은 분析에 포함되지 않습니다."

- **Major** The spec contains no handling for stale CODEF data (e.g., a cancelled policy still appearing as active in the 내보험다보여 aggregation). If a user terminated a policy but CODEF still shows it as active, the AI may generate a "청구 가능합니다" Review for coverage that no longer exists. There is no specified refresh cadence, no "data last updated" timestamp visible to users on the Insurance Project screen, and no mechanism to flag potentially stale data. *Fix:* The Insurance Project 상세 screen must display a "보험 정보 마지막 업데이트" timestamp with a manual "다시 가져오기" action. If data is older than 30 days, show a warning badge on the Health Score Card.

- **Major** The OCR flow specifies that the AI disclaimer "AI가 인식한 내용입니다. 정확하지 않을 수 있습니다." appears once above all field rows (EXPERIENCE.md line 202, DESIGN.md line 364). This is a single generic disclaimer that the spec itself notes users could miss. If OCR extracts a wrong 진료비 amount (e.g., 840,000원 instead of 84,000원 due to a smudged digit) and the user confirms without catching it, the AI Review will be generated against a 10x inflated medical expense, potentially generating false claim eligibility signals. The "confirmed state" checkmark (DESIGN.md line 358) visually rewards confirmation without verifying correctness. *Fix:* Add per-field plausibility validation: if the 진료비 field exceeds a threshold (e.g., 500,000원 for an outpatient receipt), show an inline warning: "진료비가 일반적인 외래 진료비보다 높습니다. 금액을 다시 확인해 주세요." Do not block submission — warn only.

- **Minor** The fallback to manual insurance input (EXPERIENCE.md line 71: "수동 보험 입력") has no specified UX indicator on subsequent Reviews that the underlying insurance data was manually entered and unverified. A user who manually entered incorrect policy details months ago (e.g., wrong coverage limit, wrong co-pay structure) will receive AI Reviews based on that wrong data. The Memory is immutable (EXPERIENCE.md line 437: "This chain is immutable once written"), so the error compounds over time. *Fix:* Insurance Project 상세 must distinguish manually-entered policies from CODEF-verified policies with a visual tag ("직접 입력" vs "연동 확인"). Reviews based on manually-entered data must include a mandatory HonestBox entry noting the coverage data is self-reported and unverified.

## 5. Review Before Action Enforcement — Major

### Findings

- **Major** The fast-path attack: User gets push notification → arrives at Home Inbox → taps Review card → sees Context Sticky Bar with "추천: 실손보험 청구 권장" already displayed → scrolls down slightly (enough for sections to enter viewport per the section-presence activation rule) → CTA activates → taps 채택. The section-presence activation rule says sections are "marked as seen when they enters the viewport" (EXPERIENCE.md line 124). On a fast scroll, all four sections (Summary, Recommendation, Evidence, Risk/Uncertainty) could enter viewport within a single aggressive swipe lasting under 2 seconds. There is no dwell time requirement, no reading comprehension check, and no visual acknowledgment of the Honest Box. The entire safety mechanism rests on a scroll-entry detection that can be defeated by momentum scrolling. *Fix:* Add a minimum 1.5-second dwell time requirement on the Risk/Uncertainty section specifically before activation. This is the section users are most incentivized to skip. Section-in-viewport is not the same as section-seen.

- **Major** The "Short Review exception" (CTA enabled from load) creates a fast lane that the spec does not constrain by content type or risk level. The spec says "If the Review content fits in a single viewport without scrolling, the bar is enabled from the moment the screen loads" (EXPERIENCE.md line 127). There is no prohibition on a consequential claim Review being classified as "short." If the AI backend generates a terse Review (e.g., "청구 가능 — 실손 해당, 서류 2건 필요") that fits one viewport, the user can tap 채택 in under 3 seconds of arriving at the screen. The entire "Review before Action" principle is bypassed. *Fix:* Short Review exception must be gated: only permitted if (a) the Review contains no HonestBox entry AND (b) the claim amount is below a defined threshold (e.g., 50,000원). For all other Reviews, the section-scroll activation must be required regardless of Review length.

- **Minor** The "보류" decision (EXPERIENCE.md line 257: "Review returns to Inbox. No automatic re-escalation") has no time-based reminder or expiration. A user who hits 보류 on a claim Review may forget about it indefinitely. Meanwhile, claim submission windows in Korea are typically 3 years (보험금 청구권 소멸시효), but certain procedural deadlines (e.g., hospital record retention, diagnostic certificate availability) are much shorter. The spec explicitly prohibits re-engagement push notifications for the same item beyond one follow-up (EXPERIENCE.md line 366). *Fix:* For 보류 Reviews where the originating Event was a medical expense, add a time-stamped note on the Inbox card: "보류한 날로부터 N일째입니다." After 90 days, add a one-time informational (not urgency) push: "보류 중인 보험 청구 Review가 있습니다." This is not urgency language — it is factual status.

- **Minor** The "무시" decision has no friction at the moment of choice (EXPERIENCE.md line 258: "No confirmation dialog"). For "나중에 검토" (보류), the absence of a dialog is correct — it is a reversible soft action. But "무시" archives the Review and removes it from the Inbox. Although Memory Timeline access exists, the spec does not make this visible to the user at the moment of dismissal. A user who intended 보류 but tapped 무시 by mistake (the two ghost pills are side by side — DESIGN.md line 265) has no recovery path visible on screen. *Fix:* The ghost pill layout places "나중에 검토" and "무시" side by side. Given their proximity and the semantic difference (defer vs. discard), these should not be equivalent-weight ghost pills. "무시" should be lower visual prominence (text-only, no pill border) to reduce accidental selection.

## 6. Memory & Data Accuracy — Major

### Findings

- **Critical** The spec states "This chain is immutable once written. The user does not manage or edit the Memory Timeline items directly" (EXPERIENCE.md line 437-438). This is a design choice that creates a data integrity problem: if an OCR error that the user missed resulted in an incorrectly confirmed Event, the erroneous data is permanently locked into Memory and becomes "context for future Reviews on the same Project" (EXPERIENCE.md line 436). The user has no correction path. Future AI Reviews will be personalized based on wrong data, potentially forever. Under GDPR-equivalent Korean law (개인정보보호법 Article 36), users have the right to correct their personal data. An immutable memory with no correction mechanism may be legally non-compliant in addition to being a product quality risk. *Fix:* Define a correction flow for Events: users can flag a Memory Timeline item as "incorrect" which creates a correction note (not deletion) visible in the chain. The correction note feeds the AI context. Full deletion should be available for individual items under the 개인정보보호법 right to erasure.

- **Major** The AI uses past Memory to "personalize" future Reviews (EXPERIENCE.md line 436: "The full chain... becomes context for future Reviews on the same Project"). The spec contains no safeguard for Memory poisoning: if a user's first 3 Events were incorrectly confirmed (OCR errors, manual entry mistakes), all subsequent AI Reviews inherit that corrupted context without any mechanism to detect or flag the degradation. There is no "confidence in Memory data quality" signal exposed to either the user or the AI generation system. *Fix:* The AI Review generation pipeline must assess Memory data quality before generating a personalized Review. If more than 25% of source Events are manually entered and unverified, or if inconsistencies are detected (e.g., same hospital on same date twice), the HonestBox must contain: "과거 이벤트 일부가 직접 입력된 정보입니다. 분析의 정확도에 영향을 줄 수 있습니다."

- **Major** The spec has no policy for insurance policy changes over time. If a user renews their insurance with different coverage terms, or switches insurers, the Insurance Project may still carry the old policy data from CODEF. The AI will continue generating Reviews based on the old coverage. The spec has no "policy expiry" concept, no alert when CODEF data diverges from a previous sync, and no prompt to the user to re-verify coverage details annually or upon renewal. *Fix:* The Insurance Project 상세 screen must show policy-level data with explicit term dates. For policies approaching expiry or renewal, generate a Review proactively flagging the upcoming change. After renewal date passes without a data refresh, flag the affected policies as "확인 필요" in the project and inhibit claim Reviews for those policies until re-verified.

- **Minor** Memory Timeline items link to source screens, and "if the source screen no longer exists (e.g., an archived Review), a read-only summary view is shown" (EXPERIENCE.md line 232). The spec does not define what constitutes the "read-only summary view" or how much information it preserves. If a user needs to reference the original AI analysis for a future claim or dispute (e.g., to show that the AI had recommended the claim before the insurer denied it), an undefined summary view may be legally or practically insufficient. *Fix:* Specify that archived Reviews are stored in full (not summarized) and that the read-only view renders the complete Review content with a "보관된 Review" banner. This is also relevant for any future regulatory inquiry.

## 7. Onboarding Value Promise — Major

### Findings

- **Major** The onboarding delivers "보험 5건 · 월 163,000원 · 건강도 82점" (EXPERIENCE.md line 510) as the first concrete value moment. The Health Score (82 out of 100) is presented without any explanation of what the score means, what actions would change it, or what the range implies for the user's actual insurance situation. A score of 82 could mean "you're well-covered" or "you're overpaying" or "your gap coverage is mediocre" — the user has no way to know which interpretation is correct. If users anchor on "82 is pretty good" and the AI later generates a Review pointing out major coverage gaps, the score's prior reassurance damages rather than builds trust. *Fix:* The 보험 건강도 결과 screen must include a 2–3 line plain-language interpretation of the score below the Health Score Card: e.g., "82점은 기본 보장은 갖춰져 있지만, 수술비 및 중증질환 보장에 빈틈이 있을 수 있음을 나타냅니다." This interpretation must be generated by the AI as part of the initial analysis, not a static template.

- **Major** The onboarding flow generates an "initial Review" immediately after integration (EXPERIENCE.md line 512-513: "Home Inbox에 '보험 현황 초기 Review — 보장 분析이 준비됐습니다' 카드"). The narrative of Flow 2 (이준서) suggests this happens within the onboarding session. However, the spec has no treatment of what this initial Review contains if CODEF returned only partial data. The user's first-ever Review — their most trust-forming experience — could be systematically incomplete if CODEF's data was partial, and the user would have no signal that the scope of the analysis was limited. *Fix:* The initial Review must declare its data completeness in the HonestBox: "이 분析은 연동된 N건의 보험 정보를 기반으로 합니다. 미연동 보험이 있다면 해당 보장은 포함되지 않습니다."

- **Minor** The onboarding welcome heading "내 보험, 지금 제대로 알고 있나요?" (EXPERIENCE.md line 498) implicitly tells the user they are probably underinformed. This is a mild anxiety trigger that conflicts with the "Minimize anxiety" principle (EXPERIENCE.md line 34). The question presupposes ignorance. *Fix:* Rephrase to a value-forward prompt: "내 보험을 한눈에 정리해 드립니다." — states the same proposition without implying deficiency.

- **Minor** The two-option onboarding choice ("자동으로 가져오기 (약 30초)" / "직접 입력할게요") does not explain what "자동으로 가져오기" actually does — specifically, that it will access the government's 내보험다보여 service via CODEF API using the user's 공공아이디/비밀번호. For a security-conscious Korean user, discovering mid-flow that they are being asked to input government portal credentials into a third-party app is a trust shock. ## Top 5 must-fix issues before launch

1. **No mandated legal disclaimer text on any Review screen** (Section 2, Critical). The entire product generates claim recommendations without a persistent, design-specified "참고 정보이며 보험 모집이 아닙니다" disclaimer. This is the single highest regulatory exposure issue. Fix this before any user-facing beta.

2. **"Conclusion first" voice applied to Review titles creates false certainty before any safety mechanism activates** (Section 1, Critical). The sticky bar recommendation text is visible before the user reads evidence or uncertainty. This undermines every other trust mechanism in the spec. Title language and sticky bar disabled-state copy must be redesigned to withhold the conclusion until the user has engaged with evidence.

3. **Denied claim outcome has no UX treatment** (Section 2, Critical). When a claim is rejected after AI said "청구 가능합니다," the user experiences an AI-caused financial disappointment with no explanation, no context, and no repair path. For early users, one poorly handled rejection can produce a 1-star review that poisons the product's market entry.

4. **Memory is immutable with no correction or deletion path** (Section 6, Critical). OCR errors propagate into Memory and poison all future AI Reviews on the same project, with no user recourse. Additionally, this may violate 개인정보보호법 Article 36 (right to data correction). This must be resolved before the product handles real financial data.

5. **Short Review exception is unguarded and can bypass the entire Review Before Action principle** (Section 5, Major). Without content-type or risk-level gates on Short Review eligibility, the AI backend can effectively suppress the safety scroll mechanism for any Review by generating a terse response. This is a product integrity issue: the spec claims "Review before Action" is a core principle, but does not protect it architecturally.
