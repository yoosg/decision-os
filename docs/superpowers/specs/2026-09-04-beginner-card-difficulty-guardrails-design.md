# 입문자 카드 — 난이도 가드레일 (장벽 억제 + 셋업형 배제)

- 날짜: 2026-09-04
- 관련 스펙: [2026-09-02 만들거리 정체성(3b)](2026-09-02-beginner-card-project-identity-design.md),
  [2026-08-31 통합 바이브코딩 가이드(P3)](2026-08-31-beginner-card-vibecoding-guide-design.md)
- 관련 구현: `api/pipeline/llm/prompts.py`(`PROJECT_CARD_SYSTEM_PROMPT`)
- 범위: **백엔드 카드 생성 프롬프트 + 눈 점검 스크립트 1개.** 스키마·검증·웹·DB 무변경

## 배경 / 문제

3b 스펙의 비목표에 *"입문자 난이도 가드레일 (API 키·결제 장벽의 체계적 억제)"* 로 이월해 둔 항목이다.
프로덕션에 생성된 `project_card` 3장을 열어보니 예상보다 구멍이 넓었다.

| 만들거리 | difficulty | estimated_minutes | prerequisites |
|---|---|---|---|
| Apple Silicon에서 Omarchy 실행하기 | basic | 30 | "없어요, 바로 시작!" |
| Apple Silicon에서 나만의 Omarchy 실행해보기 | basic | 30 | "Mac 컴퓨터, 터미널 사용법에 대한 기본적인 이해가 필요합니다." |
| 나만의 간단한 그래프 데이터 시각화 앱 만들기 | basic | 30 | "없어요, 바로 시작!" |

Omarchy는 Arch Linux 기반 개발 환경이다. 입문자가 30분에 완주할 수 있는 만들거리가 아니고,
애초에 **만들거리가 아니라 설치 작업**이다. 그런데 준비물은 "없어요, 바로 시작!"으로 통과했다.

### 왜 현재 규칙이 못 막았나

프롬프트에는 이미 방어선이 하나 있다.

> `- 준비물이 결제나 복잡한 설치를 요구하면, 그 만들거리를 버리고 다시 고릅니다.`

이 줄은 **준비물**을 필터링한다. 그런데 Omarchy 카드가 통과한 이유는 준비물이 아니라
**만들거리 자체의 성격**("남이 만든 걸 설치해서 돌려보기")에 있다. 준비물 필터로는 구조적으로
걸리지 않는다. 규칙이 없어서가 아니라 **규칙이 엉뚱한 자리에 있어서** 뚫린 것이다.

또한 그 한 줄은 1단계의 마지막 불릿으로 묻혀 있어, 통과해야 하는 관문으로 읽히지 않는다.

## 목표 / 비목표

**목표**
1. **장벽 억제** — 결제·신용카드·유료 구독·하드웨어 구매·OS/가상화/도커/DB 서버 설치를 요구하는
   만들거리를 생성 단계에서 배제한다.
2. **셋업형 배제** — "○○ 설치하기 / 실행해보기 / 환경 구축하기"가 만들거리인 카드를 배제한다.
3. `prerequisites`가 실제로 쓸모 있게 적히도록 서술 규칙을 준다(막연한 "API 키 필요" 금지,
   겁만 주는 항목 금지).

**비목표 (섞지 않음)**
- **난이도 라벨 캘리브레이션** — 3장 전부 `basic`/30분으로 수렴해 `first_step|basic|challenge`
  뱃지가 정보를 못 준다. 실재하는 문제지만 원인(판단 기준 부재)이 달라 별도 슬라이스로 둔다.
- `estimated_minutes` 정확도
- P1 마일스톤 프로세스화 / P2 체크리스트 요구사항화
- `example_prompt` 개인화
- 피드 목록 제목(`signals.title`) 개편
- Flutter 렌더링

## 허용선 (설계 결정)

카드가 요구해도 되는 준비물의 기준선을 **"무료 가입·무료 키까지 허용"** 으로 정한다.

| | 항목 |
|---|---|
| 허용 | AI 코딩 도구(공통 전제), 신용카드 없이 발급되는 무료 API 키, npm/pip 패키지, 브라우저·편집기 |
| 금지 | 결제·신용카드 등록·유료 구독·크레딧 구매 / OS·리눅스 배포판·가상머신·도커·DB 서버 설치 / 하드웨어 구매 / 클라우드 배포 |

무료 키를 허용선 안에 두는 이유: 현재 프롬프트가 모범 예시로 드는 카드
(*"AI에게 질문하는 나만의 챗봇 만들기"*)가 API 키를 필요로 한다. 키까지 금지하면 프롬프트가
자기 예시와 충돌하고, AI/API 토픽에서 만들거리 폭이 크게 좁아져 개념체험형 우회가 급증한다.

대신 키 발급 자체가 입문자에게 이탈 지점이므로, `prerequisites`가 **발급 경로를 한 줄로 안내**하도록
서술 규칙으로 보완한다.

## 채택한 접근 — 프롬프트 재설계만 (접근안 A)

`PROJECT_CARD_SYSTEM_PROMPT` 한 곳만 고친다. 스키마·검증·웹·DB 무변경.

> **폐기된 대안**
> - **접근안 B — `setup_cost` 열거형 필드 추가 + 웹 뱃지**: 유저 사전 고지와 데이터 추적이 목적인데,
>   (1) 카드는 온디맨드 생성이라 **피드 목록에는 페이로드 자체가 없어** "열기 전에 알기"가 불가능하고,
>   (2) `prerequisites`는 이미 상세 화면 두 번째 블록이라 뱃지가 새로 주는 정보가 거의 없다.
>   (3) 실사용자가 극소수라 추적 데이터도 표본이 안 된다. 반면 검증 실패(=`failed` 화면) 리스크와
>   웹 하위호환 작업은 실제로 늘어난다.
> - **접근안 C — 2단계 생성(후보 3개 → 자기 검열 → 1개 선택)**: 구조적으로 가장 확실하지만
>   비용·지연 2배. 카드 생성은 온디맨드라 지연이 곧 이탈이다. 3b에서 같은 이유로 이미 폐기했다.

**하드 검증을 추가하지 않는 이유**: 재시도 인프라가 없어 검증 실패가 곧 유저의 `failed` 화면이다
(`api/pipeline/reviewer.py`의 카드 경로는 `LLMProviderError`를 그대로 올린다). 3b에서 금칙어
문자열 검사를 뺀 것과 같은 판단 — 오탐 한 번의 손해가 누락 한 번보다 크다.

## 프롬프트 변경 상세 (`api/pipeline/llm/prompts.py`)

### (1) 1단계 마지막 불릿 삭제 → "1.5단계 완주 가능성 게이트"로 승격

기존 `- 준비물이 결제나 복잡한 설치를 요구하면, 그 만들거리를 버리고 다시 고릅니다.` 를 **삭제**하고
(아래 게이트에 흡수되므로 중복), 1단계와 2단계 사이에 넣는다:

```
1.5단계 — 정한 만들거리를 아래 3문항으로 점검합니다. 하나라도 '예'면 그 만들거리를 버리고 1단계로 돌아갑니다.
- 돈이 드나요? 신용카드 등록, 유료 구독, 크레딧 구매가 필요하면 '예'입니다.
- 무거운 설치가 필요한가요? 운영체제·리눅스 배포판·가상머신·도커·데이터베이스 서버 설치나 특정 하드웨어 구매가 필요하면 '예'입니다.
- 만들거리가 '설치·설정·실행' 그 자체인가요? 남이 만든 것을 내 컴퓨터에 올려 돌려보는 일이면 '예'입니다.
```

세 번째 문항이 Omarchy 실패를 직접 겨냥한다.

### (2) `## 금지 사항`에 셋업형 금칙 1개 추가

```
- '○○ 설치하기', '○○ 실행해보기', '○○ 환경 구축하기', '○○ 세팅하기'는 만들거리가 아닙니다. 만들거리는 당신이 코드로 새로 만들어내는 것이어야 합니다. 남이 만든 도구나 운영체제를 내 컴퓨터에 올려 돌려보는 것은, 그 과정이 아무리 길어도 만들거리로 치지 않습니다.
```

3b가 넣은 *"동작하는 것이 있어야 한다"*(= 글만 늘어놓기 금지)의 짝인 **"남의 것 돌리기 금지"**.
3b가 구멍을 발견하고 금칙으로 메운 방식을 그대로 따른다.

### (3) `## 준비물 규칙` 절 신설 (`## 금지 사항` 다음, JSON 스펙 앞)

```
## 준비물 규칙

요구해도 되는 것
- 신용카드 없이 발급되는 무료 API 키
- npm / pip 으로 설치하는 패키지
- 웹 브라우저와 텍스트 편집기

요구하면 안 되는 것
- 결제, 신용카드 등록, 유료 구독, 크레딧 구매
- 운영체제·리눅스 배포판·가상머신·도커·데이터베이스 서버 설치
- 하드웨어 구매, 클라우드 서버 배포
```

### (4) 같은 절에 `prerequisites` 작성법 명시

```
prerequisites 작성법
- 아무것도 필요 없으면 "없어요, 바로 시작!"
- 무료 키가 필요하면 '어디서 어떻게 받는지'를 한 줄로 적습니다. '(서비스명) API 키 필요'처럼 막연히 적지 마세요. 예: "Google AI Studio에서 구글 계정으로 로그인하면 무료 키를 바로 받을 수 있어요 — 신용카드는 필요 없어요." (예시일 뿐이니 카드에 맞는 곳을 적으세요)
- AI 코딩 도구(Claude Code 등)는 모든 카드의 공통 전제입니다. 준비물에 적지 마세요.
- 이미 갖고 있을 법한 것(컴퓨터, 인터넷, 터미널 기본 사용법)도 적지 마세요. 겁만 줍니다.
```

마지막 두 줄이 실제 사례 *"Mac 컴퓨터, 터미널 사용법에 대한 기본적인 이해가 필요합니다"* 를 겨냥한다.
AI 코딩 도구 설치·로그인은 P3 통합 가이드가 카드 상단에서 이미 안내하므로 준비물에 중복될 이유가 없다.

### 바꾸지 않는 것

`parse_and_validate_card`, `REQUIRED_CARD_BLOCKS`(13개), `CARD_DIFFICULTIES`, `CARD_TITLE_MAX_LEN`,
`build_card_user_content`, 웹 전체, DB 스키마.

## 테스트 / 검증 계획

### 자동 테스트

검증 로직이 그대로이므로 `api/tests/test_project_card_prompt.py`는 **회귀 확인용으로만** 돌린다
(`cd api && pytest tests/test_project_card_prompt.py -v`). 전부 통과해야 한다.

프롬프트 문자열에 특정 문장이 포함되는지 검사하는 테스트는 **추가하지 않는다.** 방금 쓴 문장을
다시 읽는 동어반복이라 회귀를 잡아주지 못하면서 프롬프트 개작 때마다 깨지기만 한다.

### 눈 점검 (이 슬라이스의 실질 검증)

신규 스크립트 `api/scripts/eval_card_guardrails.py` 를 커밋한다. 가짜 `ReviewContext`를 만들어
`llm.generate_card()`를 직접 호출하고 결과를 표로 출력한다 — 시그널 DB도 파이프라인도 타지 않는다.
P1·P2 슬라이스에서도 토픽만 바꿔 재사용하기 위해 일회용 스크립트가 아닌 커밋 대상으로 둔다.
기존 `api/scripts/eval_engagement.py`가 같은 자리의 선례이므로 그 파일의 구조·실행 방식을 따른다.

겨냥 토픽 4개:

| 토픽 | 노리는 실패 |
|---|---|
| Omarchy — Arch Linux 기반 개발 환경 | 실제 실패 사례 재현. 셋업형 카드가 또 나오나 |
| SK하이닉스 HBM4 양산 | 하드웨어 구매를 요구하나 |
| Vercel Pro 플랜 가격 개편 | 결제를 유도하나 |
| Claude Opus 5 출시 | 정상 케이스 회귀. 무료 키 발급처가 제대로 적히나 |

**합격 기준** (사람이 판정, 4장 전부 만족):
1. 만들거리가 "설치·실행·구축"형이 아니다
2. `prerequisites`에 결제·OS 설치·하드웨어 요구가 없다
3. `prerequisites`에 AI 코딩 도구 설치나 "터미널 기본 이해" 같은 겁주기 문구가 없다
4. 무료 키가 필요한 카드는 발급처가 한 줄로 적혀 있다
5. (3b 회귀) `project_title`이 뉴스 제목이 아니고, 만들거리에 동작하는 것이 있다

**before/after 비교**: 프롬프트 변경 전/후로 같은 4토픽을 각각 한 번 돌려 결과를 나란히 비교한다
(LLM 호출 8회). 자동 테스트가 못 잡는 영역이라 이 비교가 유일한 효과 확인 수단이다.

### 실행 시 주의

- **`LLM_PROVIDER=openai`로 돌린다.** 로컬 `.env`가 gemini일 수 있는데 프로덕션은 openai다.
  gemini로 확인하면 실제 배포되는 것과 다른 모델을 검수하는 셈이다.
- **이 변경은 배포해도 프로덕션 화면에 안 나타난다.** 프로덕션은 카드모드 OFF라 실사용자에게는
  리서치 리뷰가 나간다. 성과 확인은 로컬 눈 점검으로만 가능하고, 실사용자 노출은 카드모드를 켜는
  별도 결정에 달려 있다.

## 리스크

- **금칙이 늘수록 도피 위험**: 규칙이 촘촘해지면 LLM이 안전한 쪽(개념체험형 우회)으로 몰려
  카드가 토픽과 멀어지고 밋밋해질 수 있다. 눈 점검 기준 5(3b 회귀)가 이 신호를 잡는 역할을 한다.
- **프롬프트 길이 증가**: 시스템 프롬프트가 길어져 앞쪽 지시의 상대적 비중이 낮아질 수 있다.
  1.5단계를 **게이트 형태**로 짧게 유지하고, 흡수된 기존 불릿은 삭제해 순증을 억제한다.
- **검증이 없어 새는 카드를 자동으로 알 수 없다**: 의도한 트레이드오프(실패 화면 회피).
  새는 정도는 눈 점검으로만 파악한다.
