# 입문자 바이브코딩 학습 전환 (실무자 → 개발 입문자)

- 날짜: 2026-08-23
- 대상 전환: **IT 실무자 → 개발 입문자(완전 초보 포함)**, 도메인은 "개발/기술" 내 유지
- 관련: [[signal-quality-roadmap]] learnability 필터, [[engagement-diagnostic-2026-08]] 실사용자 극소수, [[review-generation-ondemand]] 카드 생성 비용 구조

## 배경 / 동기

현재 서비스는 오너 본인용에 가까운 **AI 뉴스 큐레이터**다. 여러 AI 도메인에서 토픽을 수집해
"오늘의 브리핑"으로 흘려보내고, 실무자가 *무엇을 따라잡을지* 결정하도록 돕는다. 온보딩·관심사·리뷰가
모두 실무자 언어(RAG·MCP·Agent Architecture 등)로 짜여 있고, 실사용자는 극소수(~1–4명)다.

전환의 목표는 대상을 **개발 입문자**로 넓히는 것이다. 요즘 유행하는(그러나 **표준이 될 만한**) 기술
토픽을 기반으로, 입문자가 **직접 뭔가를 만들어보는(바이브코딩) 경험까지** 완주하도록 안내한다.

핵심 통찰: 실무자는 "뭘 배울지"를 스스로 결정할 수 있지만, **입문자는 그 결정을 못 한다**(무엇이
중요한지, 무엇이 선행돼야 하는지 감이 없다). 따라서 제품 성격이 **뉴스 큐레이터 → 개인 학습 코치**로
이동한다. 입문자가 미리 인지해야 하는 3가지 — **뭘/어떻게 시작? · 뭐가 나와? · 뭘 얻어?** — 가
새로운 핵심 산출물의 스펙이 된다.

## 불변 (유지하는 것)

- **엔진 루프**: `토픽 → 가이드 → 실행 → 결과 → 기억`. 옷만 갈아입고 루프 자체는 그대로.
- **아키텍처 원칙**: 읽기는 Supabase 직접, 쓰기는 FastAPI 경유. Playbook은 내부 모듈.
- **행동이력 기반 개인화**: "해봤다/저장/관심없음" 이력 축적 → 추천 고도화.
- **롤아웃**: 기존 `AI Research` Playbook을 **입문자용으로 갈아끼움**(교체). 실무자 버전은 접는다.
  실사용자 극소수 + 오너 본인 도구라 두 버전 병존은 낭비. 되돌림은 git.

## 1) 핵심 산출물 — "프로젝트 카드"

기존 'AI 리뷰'가 붙던 자리를 대체한다. 트렌드 토픽을 **버려지지 않는(evergreen) "만들어볼 거리"**로
변환한 카드. 매일 갱신되는 뉴스 아이템이 아니라, 한번 만들면 재사용되는 학습거리다.

카드 필드(모두 **LLM 생성 텍스트**):

| 필드 | 의미 | 상태 |
|---|---|---|
| 🚀 **어떻게 시작** | 진입점 + **복붙 가능한 시작 프롬프트/템플릿/체크리스트** | 핵심 |
| 📦 **뭐가 나와** | 완성하면 손에 쥐어질 결과물(deliverable) | 핵심 |
| 🎓 **뭘 얻어** | 이걸로 갖게 되는 역량(gain) | 핵심 |
| 🧰 **준비물/세팅** | 0번째 계단(계정·에디터·실행환경 등 사전 준비) | v1 필수 추가 |
| 🆘 **막히면 이렇게** | 자주 나는 에러 + **복붙할 복구 프롬프트** | v1 필수 추가 |
| ✅ **성공 기준** | "이렇게 보이면 성공"(완성 기준 / 예시 화면) | v1 필수 추가 |
| 🗺️ **진행 과정** | 큰 마일스톤 3~5개(각 뭘 함+끝나면 이렇게 보임) | v1 추가 |
| 🏷️ **난이도** | 뱃지(예: 첫걸음/기본/도전) | v1 권장 추가 |

### 개인화 모델 — 카드는 제네릭, "예시 하나"만 개인화

카드 자체(제목·주제·가이드 핵심)는 **모든 유저에게 동일한 표준**으로 고정한다. 개인화는 **가이드 안의
"개인화 예시 프롬프트" 블록 딱 하나**에만 스며든다.

- 제목/주제 고정: 예) *"간단한 웹폼 만들고 데이터 저장하기"* — 피드·히스토리·중복제거 전부 이 원본 기준.
- 가이드 **핵심**(개념·프롬프트 뼈대·명령·성공기준) 고정 = 누구에게나 같은 표준 스킬(= 진짜 배우는 것).
- **🎯 개인화 예시 프롬프트**: 온보딩 도메인으로 렌더된 **복붙 가능한 예시** 1개.
  예) *"카페면 이렇게: '카페 예약 폼 만들어줘. 날짜·시간·인원 입력받고…'"* + 원탭 복사.
- 도메인이 억지스러우면 제네릭 예시로 fallback(적용가능 플래그 불필요).

> **폐기된 대안**: "제목/결과물까지 도메인으로 렌더하는 2레이어(canonical↔instance) + 렌즈 적용가능
> 플래그"는 오버스펙으로 폐기. 라이브러리 폭발·학습가치 가림·히스토리 정합성 비용이 컸다. 개인화를
> "첫 프롬프트 예시" 한 곳에 집중하는 편이 값싸고 효과가 크며 학습가치도 안 가린다.

### 상세화면 고정 골격 (= LLM 생성 스키마 = 입문자 여정 순서)

모든 카드가 **동일한 7블록**을 채운다. 구조를 고정하면 (1) 입문자가 매번 안 헤매고(예측가능성=안정감),
(2) 이 골격이 곧 카드 생성 스키마라 품질이 균일해지며, (3) "마지막 1미터"(준비물·막힘·성공판정)가
골격에 강제돼 빠질 수 없다. 개인화되는 칸은 ③ 안의 예시 프롬프트 **딱 하나**.

```
헤더        제목(제네릭) · 🏷️난이도 · ⏱예상시간 · 🎓 이걸로 배우는 것(스킬 라벨)
① 📦 완성하면 이게 나와   결과물 + "이렇게 보이면 성공" 미리보기 (목적지부터)
② 🧰 시작 전 준비물       계정·에디터·환경 (0번째 계단)
③ 🚀 이렇게 시작해        표준 진입점/명령(고정) + [🎯 너를 위한 예시 프롬프트(개인화)·📋복사]
④ 🗺️ 진행 과정           큰 마일스톤 3~5개 · 각 [뭘 함]+[끝나면 이렇게 보임] · 체크박스(진도감)
⑤ 🆘 막히면 이렇게        자주 나는 에러 + 복구 프롬프트 (④ 마일스톤과 연결)
⑥ ✅ 다 됐는지 확인       성공 체크리스트
⑦ 결과 남기기            [🎉 성공] [😵 막힘] [🏳️ 포기] (+선택 한 줄)
```

**④ 진행 과정 = "거친 지도"**: 한 줄 지시가 아니라 마일스톤 **3~5개**만(각 = 뭘 함 + 끝나면 이렇게
보임). 상세 설계는 유저가 바이브코딩하며 스스로 브레인스토밍 — 다 짜주면 억지스럽고 재미를 뺏는다.
너무 잘게 쪼개면 "지시서"가 되므로 **3~5개·거칠게**를 생성 규칙으로 못박는다. 제네릭 고정(개인화 X).
어느 마일스톤에서 막혔는지가 곧 ⑤/결과기록의 "막힘" 신호가 된다.

특정 카드에 불필요한 블록도 비우지 않고 짧게 채운다(예: 준비물 없음 → "없어요, 바로 시작!").
유연성보다 **일관성**을 택한다(입문자에겐 일관성이 이득).

**BMAD 등 개발 방법론 비채택**: 진행 과정을 BMAD(분석가·PM·아키텍트·스토리 등 팀용 헤비 방법론)로
구성하는 안은 폐기. 입문자에겐 우리가 애써 걷어낸 전문용어·압도감을 되돌린다(첫 자전거에 비행 전
점검표 격). 빌릴 아이디어는 "일을 명확한 단계로 쪼갠다" 하나뿐이고, 그건 ④의 3~5 마일스톤으로 이미
입문자 언어로 **자체 구현**했다. 프레임워크 의존 없이 서비스가 자체 구성한다.

**행동이 앱 밖에서 일어남**: 실제 코딩은 유저가 자기 도구(Claude/Cursor/ChatGPT 등)에서 한다.
앱은 "빈 화면 앞에서 뭐라 쳐야 할지 모름"을 정확히 해결(시작 프롬프트)하고, 막힘·완료 판정까지 받쳐준다.
**인앱 코드 실행/에디터는 v1 비범위**(사실상 다른 제품).

**"마지막 1미터" 원칙**: 카드는 "시작"만이 아니라 "시작 다음"(준비물→막힘→성공판정)까지 책임진다.
이게 없으면 입문자는 *인지는 되는데 완주는 못 하는* 지점에서 조용히 이탈하고, 핵심 약속이 깨진다.

## 2) 수집 & 필터 — "표준 학습가치" 필터

"최신 전부"가 아니라, 핫 키워드 중 **표준이 될 만한 것**만 통과시킨다. 실무자용 필터가 "얼마나
새로운가"였다면, 입문자용 필터는 **"얼마나 표준이고 배울 값어치가 있나"**다. 유행 노이즈에 휩쓸리지
않고 *어디 가서도 통하는 기본기*를 쌓게 한다. ([[signal-quality-roadmap]]의 learnability 방향 연장선.)

- 주 1회 배치가 핫 키워드를 훑어 → 표준 필터 통과분만 → 카드로 변환해 **라이브러리에 추가**.
- 수집 주기(주1회)는 코드 상수로 조정 가능. 실사용자 극소수 + 비용 고려하면 주1회로 충분.

## 3) 온보딩 개편 — 대상 확장 + "결과물" 축

기존 6문항(역할/스택/RAG관심/일일학습시간)을 **폐기**하고, 입문자 언어로 4문항만 남긴다(칩 선택 위주,
5초 내 완료). 입문자는 "무슨 **기술**?"이 아니라 "무슨 **결과물**?"로 사고한다.

1. **뭘 만들고 싶어?** *(결과물 종류: 웹사이트 / 앱 / 자동화 / AI 챗봇 / …)* — 옵션 최종 목록은 열린 항목
2. **어떤 쪽에 관심 많아? / 뭐 하는 사람이야?** *(도메인: 일·업무 / 취미·덕질 / 자영업·사이드벌이 /
   학교·공부 / 크리에이터 / …)* — **③ 개인화 예시 프롬프트의 재료**
3. **얼마나 해봤어?** (완전 처음 / 조금 해봄) — 난이도 개인화 신호
4. **왜?** (취미 / 이직 / 사이드 프로젝트) — 톤

`1(결과물 종류) × 2(도메인)`이 합쳐져 개인화 예시가 구체화된다(예: *카페*(2) × *웹사이트*(1) →
"카페 예약 웹사이트" 예시 프롬프트). 단, **개인화는 상세화면 ③ 예시 블록에만** 반영되고 카드 원본은
제네릭 유지(위 개인화 모델 참조).

이후엔 행동이력으로 자동 고도화. **상세 진단/실력 테스트는 비범위**("배우러 왔는데 시험부터?" → 이탈).

## 4) 개인화 & 결과 기록

- **결과 기록: `성공 / 막힘 / 포기`** 3분류(스크린샷 강제 X — 입문자 이탈 방지). "막힘"은 "너무
  어려웠음" 신호라 개인화에 금값(다음 추천 난이도 하향).
- **히스토리 유지** = 과거 발자국(그대로) + 개인화 재료. 홈 피드와는 별개 개념.

## 5) 홈 피드 — 정렬 & 갱신

### 두 개의 시계 (신문 → 넷플릭스)

- **콘텐츠 시계(수집)**: 뒤에서 도는 주1회 배치. 라이브러리에 새 카드를 **공급만** 한다.
- **유저 시계(피드)**: *시간*이 아니라 ***내 행동***으로 갱신. 신문(날짜로 새 1면)이 아니라
  넷플릭스(방금 한 편 다 봐야 다음 추천 재배치)처럼 동작. → "오늘 못 따라잡음" 불안 제거.

### 정렬 우선순위 (위 → 아래)

1. **▶️ 이어서 하기** — 시작했는데 안 끝낸 카드. 최상단(하던 실을 놓치지 않게).
2. **🎯 지금 추천** — 개인화된 "다음 한 걸음". 신규 유저면 온보딩 답 기반 **"첫 승리"용 쉬운 카드**.
3. **🔖 저장함** — 찜해둔 것.
4. **🧭 둘러보기** — 나머지 라이브러리(관심도순). **주간 신규 카드가 🆕로 여기 섞임**.
5. *(완료 / 관심없음 → 피드에서 빠져 **히스토리**로)*

### 갱신 트리거

- **무행동** → 순서 **그대로 유지**. 주간 배치가 돌아도 4번 구역에 새 카드만 조용히 추가, 1~2번은 안 흔듦.
- **해볼래(시작)** → 그 카드 **1번으로 승격**.
- **완료 / 막힘 / 포기** → 피드에서 내려가 히스토리로 이동 + **2번(다음 추천) 재계산**.
- **저장** → 3번으로. **관심없음** → 숨김.
- **완료 시** "🎉 해냄" 마이크로 연출 후 히스토리로(성취감 잔상).

## 6) 디자인 (순서)

입문자 대상에선 **비주얼·말투가 곧 제품 약속(친근·비위협)**이다. 개발자스러운 밀도·전문용어 톤을
벗어야 첫 화면에서 "내 거 아니네" 이탈을 막는다. 단, 풀 디자인 시스템 선완성은 미검증 화면에 과투자.

**시퀀싱**: 스펙(본 문서) → **가벼운 디자인 "방향"만** 별도 패스(톤/컬러/타이포/말투) → 개발(테마
입혀가며) → 마지막 폴리시. 디자인 방향 구체안은 별도 `frontend-design` 패스로 다룬다(본 스펙 밖).

## 범위 (v1)

포함: 카드 스펙 확장(필수 3필드 + 진행과정 + 난이도) · **7블록 고정 골격(상세화면 = 생성 스키마)** ·
**개인화 예시 프롬프트 슬롯(③)** · 표준 학습가치 필터 수집(주1회) · 온보딩 4문항 개편(도메인 포함) ·
결과 기록 3분류 · 홈 피드 정렬/갱신 규칙 · 실무자 Playbook을 입문자용으로 교체.

비범위: 인앱 코드 실행/에디터 · 다중 Playbook 병존 · 상세 진단 온보딩 · 매일 갱신 · 스크린샷 강제 제출 ·
**카드 제목/결과물 도메인 렌더(2레이어) 및 렌즈 적용가능 플래그**(개인화는 ③ 예시 한 곳에 집중).

## 열린 항목 (나중에 확정)

- 온보딩 옵션 최종 목록 — Q1 결과물 종류 + **Q2 도메인/관심** 두 축
- 수집 주기 정확값(주1회로 시작, 상수)
- 난이도 등급 체계(예: 첫걸음/기본/도전)
- 카드 라이브러리 **초기 시드** 방법(콜드 라이브러리 문제 — 첫 배치 전 최소 카드 확보)
- 디자인 테마 구체안(별도 패스)

## 리스크

- **카드 품질**: LLM이 생성한 가이드로 입문자가 실제 **완주** 가능한지가 제품 성패. 실사용자 적어
  데이터 튜닝 불가 → **정성 점검(n=1)**으로 검증([[engagement-diagnostic-2026-08]]).
- **콜드 라이브러리**: 주1회 공급이라 초기엔 카드가 적다. 초기 시드로 완화 필요(열린 항목).

## 구현 분할 제안 (플랜에서 확정)

한 스펙이지만 플랜은 슬라이스로 나누는 게 안전:
1. 데이터/카드 스펙 확장(필드 3+진행과정+난이도) + **7블록 고정 골격 생성 스키마** + 생성 프롬프트
2. **개인화 예시 프롬프트(③)** 렌더 — 온보딩 도메인 → 예시 생성 + 원탭 복사
3. 수집 표준 필터 + 주1회 배치 + 초기 시드
4. 온보딩 **4문항** 개편(대상 확장 + 도메인)
5. 홈 피드 정렬/갱신 + 결과 기록 3분류
6. 디자인 방향 패스 → 테마 적용 → 폴리시
