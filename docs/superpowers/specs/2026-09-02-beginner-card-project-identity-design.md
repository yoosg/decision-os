# 입문자 카드 — 만들거리 정체성 (슬라이스 3b)

- 날짜: 2026-09-02
- 관련 스펙: [2026-08-23 입문자 바이브코딩 전환](2026-08-23-beginner-vibecoding-pivot-design.md)
- 관련 구현: `api/pipeline/llm/prompts.py`(카드 프롬프트·검증), `api/pipeline/reviewer.py`(생성 경로)
- 범위: **백엔드 카드 생성 프롬프트 + 스키마 2필드 + 웹 헤더 렌더**

## 배경 / 문제

온디맨드로 생성된 카드는 지금 **자기 제목이 없다.** 상세 화면 `h1`이 `signals.title`(뉴스 요약 톤)을
그대로 쓰기 때문에, 학습 카드의 얼굴이 *"Claude Opus 5의 발전과 특징"* 이 된다. 실제 만들거리
(*"Claude로 질문에 답하는 나만의 챗봇 만들기"*)는 메타 줄의 `skill_label`에 작게 숨어 있다.

제목이 뉴스면 그 아래 블록들도 뉴스 해설로 끌려간다. 카드 생성 프롬프트(`PROJECT_CARD_SYSTEM_PROMPT`)가
11개 키를 **평평한 목록**으로 던지기 때문에, LLM에게 "이건 프로젝트다"라는 중심축이 없다.

전환 스펙이 약속한 "버려지지 않는(evergreen) 만들거리"가 성립하려면 카드가 **자기 제목을 소유**해야 한다.

## 목표 / 비목표

**목표**
- 카드가 자기 제목(`project_title`)을 갖고, 상세 헤더가 그것을 쓴다. 뉴스 제목은 *출처*로 강등.
- 만들거리로 바꾸기 어려운 토픽(하드웨어·기업소식)에서도 억지 카드가 아니라 **개념 체험형**으로 착지한다.
- 프롬프트가 "먼저 만들거리를 정하고 나머지를 종속시킨다"는 사고 순서를 강제한다.

**비목표 (별도 슬라이스, 섞지 않음)**
- 피드 목록 제목(`signals.title`) 개편 — 카드 제목 품질을 눈으로 확인한 뒤 판단
- `example_prompt` 개인화 (온보딩 도메인 반영)
- 블록 밀도 심화 (마일스톤별 프롬프트 등)
- 입문자 난이도 가드레일 (API 키·결제 장벽의 체계적 억제)
- Flutter 렌더링 — 모바일은 프로젝트 카드를 렌더하지 않음

## 채택한 접근 — 단일 프롬프트 재설계 (접근안 A)

카드 생성은 **LLM 1회 호출**을 유지한다.

> **폐기된 대안**
> - **2단계 생성**(토픽 → 만들거리 도출 → 카드 생성): 정체성이 구조적으로 보장되지만 비용·지연 2배.
>   카드 생성은 온디맨드라 지연이 곧 이탈이다. 실사용자가 극소수인 지금은 싸게 뽑아 눈으로 보고,
>   품질이 모자라면 그때 승급한다.
> - **검증 실패 시 1회 재생성**: 재시도 인프라가 없어 새로 만들어야 하고, 최악의 경우 지연이 2배가 된다.

## 스키마 변경

`REQUIRED_CARD_BLOCKS` 11개 → **13개**.

| 필드 | 상태 | 내용 |
|---|---|---|
| `project_title` | **신규** | 만들거리 제목. 결과물 중심, 30자 내외. 회사명·모델 버전 나열 금지 |
| `topic_link` | **신규** | "왜 이 토픽에서 이게 나왔나" 한 줄. 개념 체험형 우회 시 납득 장치 |
| `skill_label` | **재정의** | 제목 역할 박탈 → 순수 "배우는 스킬"(예: *API 연결과 대화 상태 관리*) |
| 나머지 9개 | 유지 | 프롬프트상 전부 `project_title`에 종속되도록 서술 순서 재배치 |

`difficulty` / `estimated_minutes` / `milestones` / `troubleshooting` / `success_checklist`의 형식
규칙은 그대로다. 저장 봉투(`{schema_version, review_type, payload}`)와 `review_type="project_card"`도 불변 —
DB 마이그레이션 없음.

## 프롬프트 재설계 (`PROJECT_CARD_SYSTEM_PROMPT`)

평평한 키 목록 앞에 **사고 순서**를 못박는다.

1. **먼저 만들거리 하나를 정한다.** 입문자가 AI 코딩 도구로 몇십 분 안에 완주할 수 있는 것.
   - **direct 우선**: 토픽의 기술을 직접 써서 만든다.
   - **불가 시 concept 우회**: 토픽의 핵심 개념만 손으로 체험하는 미니 프로젝트로 돌린다.
     예) *Rego vs CEL 정책 언어 논쟁* → "내 앱에 간단한 접근 규칙 만들어보기"
   - direct/concept 구분은 **생성 시 사고 도구일 뿐 필드로 저장하지 않는다**(유저에게 노출 가치 없음).
     대신 우회했다는 사실은 `topic_link` 한 줄로 자연스럽게 드러난다.
2. **정한 만들거리를 기준으로** 나머지 블록을 채운다. 결과물·성공 모습·준비물·마일스톤·트러블슈팅이
   전부 그 프로젝트 이야기여야 하며, 토픽 해설이어서는 안 된다.

**금칙 규칙**(프롬프트에 명문화)
- "뉴스 요약 봇 / 정리 봇 / 트렌드 대시보드" 류의 **도피성 만들거리 금지**. 어떤 토픽에도 갖다 붙는
  답이라, 반복되면 카드 라이브러리가 죽는다.
- `project_title`에 회사명·모델 버전 나열 금지, 뉴스 헤드라인 어투 금지.
- 준비물이 결제나 복잡한 설치를 요구하면 그 만들거리를 버리고 다시 고른다.

`build_card_user_content`는 그대로 둔다(토픽명 + 출처 목록 + JSON 지시). 사고 순서는 시스템 프롬프트의
몫이다.

## 검증 (`parse_and_validate_card`)

재시도 인프라가 없어 **검증 실패는 곧 유저의 `failed` 화면**이다(`api/pipeline/reviewer.py`의 카드 경로는
`LLMProviderError`를 그대로 올린다). 따라서 하드 룰은 최소로 건다.

- `project_title`, `topic_link`: 기존 문자열 필드 검사 목록에 합류 — 비어있지 않은 문자열
- `project_title` 길이 상한 **60자** — 뉴스 헤드라인 복붙을 막는 안전핀. 목표는 30자 내외지만,
  상한은 넉넉히 잡아 정상 카드가 탈락하지 않게 한다.
- **금칙어 문자열 검사는 하지 않는다.** 오탐 한 번이 실패 화면 한 번이라 손해가 더 크다.
  금칙은 프롬프트 규칙으로 억제하고, 눈 점검으로 확인한다.

## 웹 렌더 (하위호환 포함)

`ProjectCardPayload`에 두 필드를 **optional**로 추가한다. 백엔드 검증은 필수지만 웹 타입은 optional —
새 카드는 항상 제목을 갖고, 이미 저장된 옛 카드는 깨지지 않는다.

두 화면이 같은 정체성 블록을 쓰되 노출 형태가 다르므로, `project-card-blocks.tsx`에 공용
컴포넌트 `ProjectCardIdentity`를 두고 `variant`로 갈라 쓴다.

- **카드 상세**(`web/src/components/home/review/project-card-content.tsx`, `variant="detail"`)
  헤더 `h1` = `payload.project_title ?? signalTitle`, 그 아래 `topic_link` 한 줄 +
  `📰 출처 토픽 · {signalTitle}` 라벨.
- **체인 상세**(`web/src/components/history/chain-detail-content.tsx`, `variant="chain"`)
  SIGNAL 노드의 `h1`은 **뉴스 제목 그대로 유지**한다 — 그 노드가 가리키는 대상이 실제로 시그널이기
  때문이다. 카드 제목은 REVIEW 노드 안, `ProjectCardMeta` 위에 `h2`로 넣고 `topic_link`를 뒤따르게
  한다. 출처 토픽 라벨은 SIGNAL 노드와 중복되므로 렌더하지 않는다.
- 두 경우 모두 값이 없으면(옛 카드) 해당 줄을 렌더하지 않는다.
- `ProjectCardMeta`는 그대로. `skill_label`은 재정의됐을 뿐 위치·표기(`🎓 {skill_label}`)는 유지한다.

## 테스트 / 검증 계획

**pytest** (`api/tests/test_project_card_prompt.py` 확장 — 실행: `cd api && pytest tests/... -v`)
- 유효 카드(신규 2필드 포함) 통과
- `project_title` 누락 → `LLMProviderError("필수 블록 누락")`
- `topic_link` 누락 → 동일
- `project_title` 빈 문자열 → 실패
- `project_title` 61자 → 실패, 60자 → 통과
- `REQUIRED_CARD_BLOCKS`에 두 필드가 포함되어 있음

**웹**: 이 브랜치에 테스트 러너가 없다(`web/package.json`에 test 스크립트 없음). 기존 관행대로
`*.test.tsx`는 문서용으로 갱신만 하고, 실제 검증은 `tsc` + Playwright 눈확인으로 한다.

**눈 점검 (정성, n=1)**: 성격이 다른 토픽 3개로 실제 생성해 본다.
1. 직접형 — 모델/도구 출시 뉴스
2. 개념형 — 정책 언어 논쟁 같은 추상 토픽
3. 변환 난이도 최상 — 하드웨어·기업 소식

3번에서 "뉴스 요약 봇" 류가 나오면 **프롬프트 규칙 실패로 판정**하고 문구를 고친다. 이 판정이 이번
슬라이스의 성공 기준이다.
